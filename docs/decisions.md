# Decisions

**Reference upstream plugins, never vendor them.** Third-party plugins are installed from their own marketplaces with `autoUpdate: true`, so we always get the latest version. Mantis is the exception, pinned on purpose (see below).

**Hooks live in the osho-core plugin, not in `settings.json`.** Versioned, and installed or removed in one command. Exception: rtk's hook, which `rtk init -g` manages itself.

**code-review-graph is opt-in per repo.** Its update hook does a full build when no graph exists, so our hooks only run where `.code-review-graph/` exists. Activate a repo with `code-review-graph build`. Its skills are regenerated by the bootstrap to match the installed CLI.

**Superpowers is installed but not injected.** Its SessionStart hook loads the full `using-superpowers` skill into every session. We empty that hook and instead offer Superpowers once per session when the task warrants it. The first session after a Superpowers update still gets the bootstrap once.

**The audit of an Escouade ticket runs from the main session, by send-back.** Majors go back to the same agent (`reject_ticket`), the user approves from the session (`approve_ticket`), and there is no audit pull request. A ticket created per finding would start from a branch that does not hold the audited code, and an audit PR merged on GitHub as well as by the Kanban merged a project's tickets twice.

**What's up ? is copied into each repo, never referenced from the plugin.** The component and the guard live in the app's repo (`<served folder>/whats-up.js`, `.whatsup/garde.py`): a git hook cannot point at the plugin cache, whose path moves with each version, and the app must work without Claude. One web component (Shadow DOM, no dependency) serves every stack, so no app gets its own insertion code to maintain. Its scenes are captures of the real app, not redrawn mockups: a vector snapshot of the DOM and its CSS was tried and drifted from the app at every quirk of its styles, while a capture is the app itself. It is its own plugin (`osho-whats-up`) so a project's other developers can install it without osho-core's personal hooks.

**Homebrew Python and Node, first on PATH.** No pyenv/nvm; `uv tool` runs on Homebrew's Python.

**Mantis is pinned to an accepted commit of the fork `OshOEz/mantis` (`plugins/osho-mantis/mantis.lock`), updated only through `/mantis-update` on the maintainer's yes.** Each osho-mantis subagent reads the `SKILL.md` of its stage from the clone in `~/.local/share/mantis`; its 19 descriptions cost nothing in other sessions, and Mantis (Apache-2.0) stays outside this MIT repo. Subagents follow those prompts, so third-party text runs only once reviewed, and the fork survives if upstream disappears. An audit keeps the commit it started with (`mantis_commit` in its `state.json`) across resumes, even if the pin moves meanwhile, and `/mantis-update` analyses on a temporary clone, so it never repoints the shared copy under a running audit.

**Audit folders are versioned by default, with a guard for public repos.** An audit contains detailed vulnerabilities and exploits. The skill checks visibility with `gh`, recommends not versioning when the repo is public, and asks when visibility is unknown.

**audit-loop audits Escouade tickets only, never through GitHub issues.** Development runs on Superpowers, which already reviews each task; audit-loop's own value is the independent pass that gates `approve_ticket` on the audited commit. A pull request outside Escouade gets `/code-review`. Findings stay in a local state file, so a flaw is never published before it is fixed.
